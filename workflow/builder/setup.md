# DS Create Builder · setup

## Web-first bootstrap

`node kit/builder/cli.mjs builder [--slug {slug}]` starts the same detached server immediately, without tokens, ledger or Figma. With no slug and no existing sessions it allocates a stable session UUID; otherwise it returns a choice of saved sessions and explicit resume/new commands without launching another server. `sessions` lists these read-only and `builder --new` explicitly creates a separate session. `builder --slug {slug}` resumes/reuses that exact system. Context exposes a copyable resume command; the chosen DS name later lives in the ledger. Its `manager/setup.json` persists the onboarding stage. Existing initialized systems do not get an onboarding record. The new command completes at the verified browser handoff; init itself remains incomplete until the Figma gates pass.

Context uses a two-step intake with existing Builder controls: General collects the project name, context and files; Interface details collects Light/Dark modes, Questionnaire §1 device/platform choices and shows an informational tokenization support note: Web docs currently use Tailwind; App docs will include token references for React Native, Swift and Kotlin. New systems have no naming question. Existing-system naming questions (Keep existing naming / Normalize) are raised only after reading the context and inventory when still unresolved. Next/Back retain entries and start no work; only Prepare submits. Fonts and colors come from context/files. Structured interfaceDetails are server-validated, saved with the original context, passed in source-bound worker requests and restored for revisions. Web preparation always records fastMode:true and follows the fast workflow; it cannot select a Default engine. Context opens a shared-style modal with required Project name, Context / Instruction and Context files. Project name is 1–100 trimmed single-line characters, with spaces/Unicode supported. On first save it also determines setup.inputSlug (Acme Design System → acme-design-system): lowercase kebab case, normalize accents, preserve Unicode letters/numbers, bound to60 characters, reject names without letters/numbers. The input slug is separate from the stable output/session Project ID used by the copyable resume command. Persist the mapping once; later display-name revisions keep it. Legacy submitted sessions without inputSlug retain their original input folder. Reject an occupied unrelated destination without merging; copy any existing files belonging to this session into a new named input tree and retain their originals. Persist it in setup.projectName and the context source, pass it in the trusted worker request, and use it for ledger.system and foundation-plan.projectName. Header, saved-context summary, resume disclosure and session list show this chosen name before generation too. An unnamed session shows Not named yet in the disclosure. Preserve the actual product name independently in plan.product.name. Renames use the existing revision/regeneration gate and never move folders. Submit saves text in chat and original file bytes/names in input/{inputSlug}/uploads/{batch}/, never overwriting another upload. Multipart requests are bounded (10 files,25MB/file,50MB total,20k context chars); input directories reject symlink escapes. JSON encoding of the context field preserves original newline bytes through multipart transport. Sources/answers are indexed by the agent after reading them. Uploaded files are never exposed as static URLs.

`GET /api/setup-flow` returns saved context/files, current job/questions and an instance CSRF token. Same-origin guarded POST routes: `/api/setup-submit` (initial multipart), `/api/setup-revise` (multipart with the expected inputRevision), `/api/setup-answers` (current job id + answers), `/api/setup-retry` and `/api/setup-cancel` (empty JSON). No browser-supplied agent command, prompt template or output directory. Preparation and Publish cannot overlap. The CLI status includes setup stage; lifecycle stop leaves active MCP work owned by its connection and uses the separate cancellation protocol.

Read all web-session inputs/answers/knowledge from workspace/input/{setup.inputSlug}/ (legacy fallback: session ID), never from the output ID by inference. Trusted setup and Figma requests carry inputSlug; readiness, input freshness and approval hashes resolve the same tree. Outputs remain workspace/output/{session}/. Preparation saves an input-bound MCP request; any compatible client can claim it with an exclusive connection lease. No AI binary is resolved or launched by production Builder. Questions and outcomes return through typed MCP tools, and readiness remains independently checked. The owning main agent keeps its MCP connection open until finishing; startup does not launch another agent or transport daemon. setup-flow also derives read-only progress from the current job’s JSONL events: a safe activity phase, human agent updates, elapsed/last-activity timestamps and recent updates. Raw commands and outputs are not exposed; common credential patterns in messages are redacted. Continuation timing starts at its own request creation, not the original submission. Quiet periods over90seconds and reported connection issues get an honest waiting note, not a fabricated percentage or failed status. Progress never changes the saved setup stage, readiness, approval or source hash; terminal status still requires the structured result and existing checks. Questions are returned to the web and answers saved before the next continuation. The snapshot hashes the full selected input tree plus regular files directly in workspace/input/ (paths, bytes, additions/removals), including knowledge and previous chat/answers. Selected-tree generated sources.md and answers/01-init.md and root repository README.md/.DS_Store are excluded. Shared root files keep exact ../{filename} source keys relative to the selected folder and are read in place; another system directory is never traversed. setup-flow lists root file metadata without exposing contents; root-only context is valid without uploading a duplicate. Root directories and symlinks are not followed; selected-tree symlinks and nonregular source files block preparation. Jobs check it before/after work; readyInputHash and inputRevision bind local readiness to the same source snapshot. Publish and synced/build gates recheck it even without polling Context. Read every server-listed root entry before asking missing design questions; never read an unlisted parent path or other system folder. Sources.md is an index, not an authority that limits the dependency set. A missing pending tool request or active MCP owner leaves an honest disconnected status. Node waiting is carried by that tool request; it cannot wake an ended chat. Disconnect or process death blocks its owned attempt without losing context; retries create a fresh attempt, and stale leases cannot affect it. Partial source data stays hidden until the canonical draft/aliases, core foundations, platform, answers, sources, provisional report and pending Figma ledger pass the local handoff checks. These artifact checks do not replace user review or prove the design quality of agent decisions. A ready draft unlocks the separate Figma approval workflow; it does not mark init complete. No token-controller sync or automatic build is introduced.


Preparation lives in a persistent, responsive Overview document using the same web-docs wrapper. The intake modal is only for entering or revising context. Four task rows track Read context, Resolve design decisions, Prepare foundations, and Validate saved draft. The MCP preparation progress tool reports context|decisions|foundation stage starts and public updates; the finish tool records validation before checking output. Only typed Builder events affect activity; historical provider stdout/stderr is not parsed for progress. These are activity signals, not completion authority: prior rows say Awaiting checks until the existing ready-result/artifact checks pass. Old jobs without markers remain inspectable without inventing stage completion. Failed, cancelled, interrupted and needs-input runs never gain green completed steps.

Activity contains at most12 public updates/fixed tool summaries; shell arguments, outputs and private reasoning are omitted. Saved context cards name selected uploads as Saved context file, not as evidence of reading. Required design questions appear inline with clickable suggestions and free-text answers. Draft answers persist in this browser tab through polling, navigation and reload; only explicit Save answers & continue writes them to the workspace and launches a continuation. Context edits retain their revision guard. Stop/retry remain explicit. Connection/quiet notices describe observed conditions, not guessed failure. Ready Overview offers Preparation activity to reopen this run and Review foundations to return to the canvas; foundation tabs retain their pan/zoom workspace.


New local preparation separates basic UI motion from illustrative/complex motion. `motionPolicy: "basic-ui"` requires the spec's five durations, four easings, three delays and Standard/Reduced modes; a screen-level illustration exclusion cannot remove these. Legacy plans remain readable, and a requested scope correction creates a new input revision/preparation through the normal setup lifecycle. For a new system, Iconography is a prepared Lucide reference from the same docs registry and official installed package (`node dev/maintain/icons.mjs` regenerates the bundled catalog/license). Its Ready status means the local reference is inspectable, not that Figma icon components were generated. Existing icon libraries stay frozen. Brand assets remain separate from this motion/icon correction.

## Source revisions and foundation plan

New web preparation requests use `preparationVersion:2` and the complete runtime contract in `skill/reference/manager-preparation.md`. Node creates a typed source pack/cache, preserving text, appearance CSS facts, assets, exact paths and hashes; unsupported/binary sources require actual native inspection. Structured token exports stay on disk and import losslessly. The saved form locks project identity, platform and modes. AI resolves design choices in one decisions.json; the owned MCP compile action expands versioned defaults/pinned palettes/overrides, validates aliases/metadata/contrast and stages all canonical review artifacts. Ready requires matching source/revision, compile receipt and hashes of the artifact set plus the existing proof checks. Questions require complete source coverage. Frozen imports preserve values/metadata and report existing contrast warnings. Source extraction and independent domain compilation are cached; focus-width changes invalidate dependent effects, while palette changes still revalidate effects and contrast. No model/provider switch, real Figma action, UI redesign or automatic build is part of this compiler. Legacy saved requests keep their original handoff. Maintainer command `node dev/maintain/foundations.mjs` regenerates defaults; its test detects authoritative spec drift. Pending Node waits do not make model requests; this does not establish wake support after a host ends its tool request.

HTML text extraction starts at node boundaries so embedded data attributes are never scanned as potential text at every character. Each uncached source is parsed in a terminable Node data thread with a10second budget, separate from the MCP event loop; these are parsers, not AI subagents. A dead preparation owner is observed as Blocked consistently by flow/state/session discovery even when it left an orphan action lock. The interruption evidence is saved only under that attempt; observation never deletes the lock or rewrites root setup state. Explicit preparation retry uses a fresh job directory and keeps original sources, so an old status read cannot revert the new request. This does not retry Figma publication.

After a submitted setup, Edit context / add files is available in questions, failed/blocked/interrupted/cancelled and ready states. Stop active preparation first; Figma publication also blocks revision. Each explicit Save & prepare again appends a context file and upload batch, increments inputRevision, preserves saved answers and originals, invalidates approval, and starts preparation. A repeated original filename supersedes its older upload as current source; the worker request lists activeFiles and the latest contextFile. Revisions remain in setup.json. An old browser revision gets a conflict rather than replacing the newer one. Cancel edit makes no changes.

For web preparation, save `workspace/output/{slug}/foundation-plan.json` alongside the canonical draft:

```json
{
  "format": "ds-create/foundation-plan@1",
  "inputHash": "<trusted request inputHash>",
  "inputRevision": 1,
  "projectName": "<chosen Builder project name>",
  "product": { "name": "<from input>", "description": "<real product description>", "platform": "Web" },
  "systemMode": "new",
  "naming": "normalize",
  "decisions": [
    { "key": "ui-font", "value": "<settled choice>", "decidedBy": "user", "source": "chat/<saved-context>.md" }
  ],
  "domains": {
    "color": { "status": "included", "variables": ["<exact saved variable names>"], "styles": [] },
    "typography": { "status": "included", "variables": ["<exact names>"], "styles": ["<exact text style names>"] },
    "space": { "status": "included", "variables": ["<exact names>"], "styles": [] },
    "shape": { "status": "included", "variables": ["<exact names>"], "styles": [] },
    "elevation": { "status": "included", "variables": [], "styles": ["<exact effect style names>"] },
    "motion": { "status": "excluded", "reason": "<actual settled exclusion>", "source": "chat/<saved-context>.md" }
  }
}
```

This is schema documentation, never a sample system to generate. `systemMode` is new/existing; `naming` is normalize/keep. Record every settled product/brand/platform/token decision; decidedBy is user/AI, and AI decisions also require reason. All source paths must exist in the trusted snapshot. Map all six domains, with exact names for included values/styles or a sourced reason for exclusions; do not invent exclusions to pass validation. Included typography/elevation require usable text/effect styles. Existing systems may preserve names and frozen raw values; new semantic tokens alias raw primitives and describe their concrete UI purpose, with canonical collection/token grammar and Part C text-style names. Record scopes explicitly (empty for hidden primitives/motion), matching WEB codeSyntax for Web/Web and App, and hiddenFromPublishing:true for raw primitives. Confirm metadata with the full/PART Figma exporter; compact hash/rows exports omit it and cannot certify equality. There is no universal token-count target. The shared checker also requires the ledger/plan project name to match the explicit setup name, and validates values/types/mode coverage, aliases and styles before ready and again before Publish. These checks prove structural usability and traceability, not the quality or truth of model decisions; user review and the real Figma audit still apply.

An older web setup with no snapshot/plan is marked outdated and must prepare again; legacy export-only systems remain readable. Agents change a canonical draft through the item tools (`reference/mcp.md#item-tools`). The tools keep the plan's names, the pack and the revision current, then return the draft to review. Agents never edit `foundations.json` by hand. If source inputs changed, regenerate through Context; never fabricate manager-owned readyInputHash or inputRevision.
