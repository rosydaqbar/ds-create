# DS Create Builder · Parts

## Parts in Builder

Once the foundations are approved (`source.review` `approved` or `synced`), Builder lists Parts, Components and Sections under separate headings below the foundations in the sidebar. The Overview uses the same three groups. Approval needs no Figma: the Publish dialog's Foundations step shows **Approve foundations** while the review is pending (or the agent runs `node kit/builder/cli.mjs approve --slug {slug}` after the user approved). **Prepare Parts** (or `cli.mjs parts`, or the MCP tool `ds_create_parts_prepare`) compiles each Part locally from its template in `kit/builder/parts/templates/` and the approved foundations. It needs no agent and writes no Figma. Templates are brand-agnostic: sizes, emphases, tones, states, properties and token roles are inputs with defaults, and the system may change any of them through `ds_create_items_change` (target `part:{id}`, field `inputs`); a change to the structure needs the user's agreement first. Preparation writes a draft to `workspace/output/{session}/parts/{id}.json` with the variant properties and count, component tokens in `Components` (each aliases a foundation token or holds a value from the spec), per-size measurements, the token map and the defaults Node picked (for example the closest label weight). Button's token map has a treatment for every Tone × Emphasis × State. For every other Part, each set, private parts included, has one row per variant that changes a token. Button's page renders every variant from those tokens for review. Next to it, the store writes `parts/{page}-{id}.md` (a readable note of the inputs and decisions), `parts/{page}-{id}.js` and `parts/manifest.json`; the JSON file is authoritative. A Part, Component or Section becomes `outdated` when a foundation item it uses changes, or when a Part it uses changes its structure; a change to that Part's tokens alone does not count. A foundation rename updates the aliases in the same save, and deleting an item a Part uses is refused. Every save keeps a revision in `history/parts/{id}/`. The part files are the source the docs site and Figma both build from.

Every page in `specs/parts/` (2.1–2.19), `specs/components/` (3.1–3.8) and `specs/sections/` (4.1–4.2) has a template, and **Prepare Parts** prepares all of them. Each is prepared after the templates it uses: Spinner before Button, Avatar and Checkbox before Tag, Label before Text field, Select before Rich text editor. On a Part's first prepare, Node drops any tone or category family that has no colors in the foundations and records that as a decision. Adding a dropped tone or category family back is a structure change.

The Button page shows Primary, Secondary and Tertiary type cards for Brand and Danger above a full variant grid for each tone. It lists no component tokens or variant properties. Clicking a card or a variant selects it in the right panel. The panel assigns only semantic tokens and styles, never primitives, using the same chip button and token picker as the foundation pages. Colors are set per Tone × Emphasis × State. Height, text size, inner spacing and icon gap are set per size. Inner spacing has one field per side, arranged around a label. Under **Global Appearance**, corners, text style (Body, Heading or Display) and weight apply to every size. Changing the text style or weight preserves each button size's text-size step. Each token or style choice immediately saves a new revision of the part file through `POST /api/parts-update`, the same part store the MCP tools use. The panel has no Save button. **Reset** clears every saved choice (`reset: true`) and returns the panel to its defaults.

Builder shows every Part, Component and Section page the way it shows Button. Each page renders the item with the white-label web components, styled with this system's tokens: type cards at the top, the *Choices we made for you* section, then every variant. Select a card or a variant to see its build controls. The build controls are token pickers for state colors, sizes, spacing and text styles. Each picker offers only tokens that match its slot type. Global Appearance holds the values every size shares. Each choice saves immediately to the part file's `overrides` through `POST /api/parts-update`; `ds_create_items_change` writes to the same `overrides`. **Reset** clears the saved overrides. Builder controls configure the item; use the docs site to check interaction states. Builder pages show visual previews, not token tables. The item components come from `kit/builder/client/items/`, and `/api/stage.css` provides the session's tokens under `.ds-stage`. After changing a web component, run `node kit/web/scripts/build-manager-items.mjs` to regenerate the item components.
