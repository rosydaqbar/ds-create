# 2.17 Kbd

A Kbd shows one keyboard key, so users can read a shortcut ("⌘" then "K") or an instruction ("Press Enter to send"). It sits next to menu items, inside tooltips, in search fields and inline with text. It is display only; it never triggers the action it names.

Kbd is its own Part so every shortcut in the system — in Menu (3.6), Tooltip (2.13), Select (3.5) and help content — looks the same and lines up with the text next to it.

# 1. Purpose

- Teach keyboard shortcuts where the action lives.
- Show keys in instructions with a recognisable key shape.
- Keep one key per Kbd so combinations read clearly and wrap correctly.

# 5. Anatomy

```text
Kbd
layout: Horizontal
align: Center / Center
padding: 0 × space/xs (sm) / 0 × space/sm (md)
height: fixed by Size
min width: equal to the height
radius: radius/xs
fill: color/surface/sunken
border: color/border/default, border/width/default, inside

└─ Text                               Hug; single line; centred
```

Construction rules:
- The height is fixed per Size and the minimum width equals the height, so a single character renders as a square key and longer names ("Shift", "Enter") grow to the right.
- The border is inside, so it adds no size.
- One key per Kbd. "+" and "then" between keys are plain text in the parent, not part of the Kbd.

## Auto Layout relationship

```text
Shortcut (in the parent, not part of this Part)
layout: Horizontal
gap: space/xxs
align: Center
├─ Kbd "⌘"
└─ Kbd "K"
```

Inline in text, the parent row aligns the Kbd to the centre of the text line.

# 6. Sizes and measurements

# 10. Guidelines content

Topics for `2.17 Kbd · Guidelines`, in order. Each visual uses real Kbd instances in real compositions.

## One key per Kbd

Build a combination from one Kbd per key in a row, `space/xxs` apart. A whole shortcut in one Kbd ("⌘+K") reads as one strange key and can't wrap.

Visual — Do/don't pair (`Doc/Do-dont`):
- Don't: one Kbd with "Ctrl+Shift+P".
- Do: three Kbds "Ctrl" "Shift" "P".

## Match the platform

Show the shortcut for the user's platform — the command symbol on macOS, "Ctrl" elsewhere — not both side by side. Use the same symbols everywhere in the product.

Visual — the same menu item shown for two platforms, each captioned with its platform.

## Size follows the text

Use `sm` next to small text, in menus and tooltips; use `md` next to body text. A Kbd never makes the text line taller.

Visual — an inline instruction with `sm` and with `md`, with a line-height guide showing that `md` fits `type/body/md` and `sm` fits `type/body/sm`.

## Display only

A Kbd is never clickable. If the key also exists as an action on screen, use a Button. Don't use a Kbd for code, values or file names; use code-styled text.

Visual — Don't: a Kbd "Save" used as a button. Do: a Button "Save" with its shortcut "⌘" "S" in its Tooltip.

## Content

- Use the key's printed name with its usual capitalisation: "Enter", "Esc", "Shift", "Tab", "K".
- Use a symbol only when the platform prints it on the key (arrows, ⌘, ⌥, ⇧, ↵); keep the same choice across the product.
- Single letters are upper case.

## Accessibility

- In code, each key is a keyboard-input element; symbols have a text alternative ("Command") so screen readers read them.
- A shortcut shown next to a menu item is also exposed on the item itself, not only drawn.
- Text on the key fill meets the text contrast threshold in every colour mode.

# 11. QA

Fail QA when:
- a shortcut is drawn as one Kbd with "+" inside it;
- single characters are not square, or the minimum width differs from the height;
- the border is outside or centred and changes the Kbd's size;
- a Kbd is taller than the text line it sits in;
- menus or tooltips draw their own key shapes instead of instancing `Kbd`;
- colours, radius and sizes are raw values instead of the tokens in §9.
