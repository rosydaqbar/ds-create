Proposal · spec restructure · draft 1

From descriptive prose to a deterministic, atomic, brand-driven contract

Today the specs tell an agent what a finished library looked like. This proposal makes them say exactly how to build one from a brand: a typed brand profile, fixed derivation tables, an atomic component hierarchy, and per-component contracts that pin every layer, token binding, frame and check. Same brand profile in → same Figma file out.

1 · Initiate small, grow atomicallyInitiation builds Tokens, Foundations and Atoms only. Molecules → Organisms → Templates are promoted later from real screens.
2 · Brand profile schemaSix numeric personality axes + brand inputs, validated before generation.
3 · Derivation tablesEvery token value is computed from the profile. No “around 40”.
4 · Component contractsYAML blocks: props, variant budget, layer tree with token per property, matrix axes.
5 · Figma build contractFixed Sections, frame recipes, naming, ordering and matrix layout algorithm.
6 · ATM over the referencesObserve the reference set, take what fits, modify it into our own rules. No reference is named or copied.
01 · Diagnosis

Why every generation comes out different

I measured the current 30 Markdown files. The randomness has concrete, fixable causes.

Hedged values
~110

“Observed…”, “around 40”, “≈ 32”, “representative” in component and foundation specs. An agent must invent the real value each run.

Copied counts
20+

Variant totals stated as observations (“Observed matrix: 200 variants”) instead of derived from a property formula.

No layer schema
0

Specs show anatomy trees but never which token binds to which property, sizing mode, or layer name rule.

Brand → UI gap
16

“Interface character” offers 16 adjectives but nothing maps an adjective to a radius, height, shadow or type scale.

Root causes

AreaTodayEffect on output
Page treeA flat list of 7 foundation pages + 16 component families, ordered alphabetically, mirroring one commercial kit’s file layout.No dependency order: large compositions (media player, rich-text editor, select menus) sit beside atoms (badge) and are generated before any product exists to justify them, so their shape is guessed.
MeasurementsDeclared “observational only”, and also “do not use fixed dimensions”.The agent picks heights, paddings and widths freshly every run.
Brand inputFree-text answers and adjectives.Two runs with the same brand can choose different radii, densities and shadow recipes.
Frame structureDescribed as “regions”, “zones”, “composition model” without coordinates, Sections or ordering algorithm.Canvas layout, region widths and matrix arrangement differ per run and per page.
Token namingFive naming presets named after external systems plus “Custom”.Naming drifts per run, and the spec leans on outside systems by name.
DocumentationLong prose lists of required topics per page (~10–15 each).Every page’s docs are composed ad hoc; layout and depth vary; slow to generate and to QA.
QA“Fail QA when…” sentences.Not executable; passes depend on the agent’s judgement.

Example from base-components/04-buttons.md

Observed md baseline: - root height around 40; - root horizontal padding around 14; - root vertical padding around 10; - root item gap around 4; - icons around 20; Treat the observed measurements as proportional baselines.

Every number above is a guess with permission to change. Multiply that by every component and the output can’t be reproducible.

02 · How v2 is written

ATM applied to the reference set

v2 is produced by running Amati · Tiru · Modifikasi over the reference design systems. The spec files contain only the result of Modifikasi. The references themselves are never named in the repo.

STEP 1

Amati

Observe the references

Compare how each reference solves the same problem: library structure, token tiers, palettes, elevation, density, type, component API, states, motion, docs. Note where they agree and where they differ. A difference marks a choice we must make on purpose.

Output: comparison matrix

STEP 2

Tiru

Take what works

Take a pattern when most references agree on it, or when one reference solves something the others don’t and it helps a deterministic, brand-agnostic generator. Take the idea, never the names, counts or layouts.

Output: adopted patterns

STEP 3

Modifikasi

Make it ours

Fit every adopted pattern to our atomic levels, the brand-profile axes and the Figma build contract. The result is written as our own rules, tables and contracts.

Output: v2 spec

Amati result: today’s spec is Tiru of a single slice of a single reference. That reference itself continues past base components into application components, marketing components and full example pages, and it defines no extension process. We copied its page tree, component list, variant counts and doc kit, and skipped the other three references.

03 · Information architecture

Atomic page tree

Pages are ordered by dependency, so building top-to-bottom always has every dependency ready. Initiation creates only the levels that need no product context. Higher levels are added by Extend whenever a user asks for, designs or needs one. IDs are stable and shared between the spec file, the Figma page and the component description.

Why atoms only at initiation: an atom’s shape depends only on the brand profile, so it can be derived deterministically. A molecule or organism depends on what the product needs (which fields, which columns, which navigation), and before the first screen exists that can only be guessed.
04 · Agentic lifecycle

Initiate once, then extend at any level

The agent works with two commands. Initiate runs once per brand and stops at Atoms. Extend runs every time a user asks for, designs, or needs a new component, at any level from atom to template. Extend follows the same procedure every time, so a component added in month six is built exactly like one added on day one.

Four ways a new component arrives

Describe

User asks for it

“We need a pricing table”, “add a date picker”. The agent turns the request into a component brief.

Design

User designs it

The user draws it in Figma and asks the agent to adopt it. The agent reads the layers and maps every raw value to tokens.

Screen

A screen needs it

While building a screen, a composition is made locally from existing components and promoted when the rule says so.

Layout

User asks for a page type

“A settings page”, “an app shell”. Treated as a template request with named slots.

Step 1 · Classify the level (decision tree)

Q0Does a component with the same job already exist?yes → extend it (new prop or variant), stop Q1Does it arrange a whole page or screen into named regions, without real content?yes → Template Q2Is it a distinct region of an interface, with its own empty, loading or error states or a data collection?yes → Organism Q3Is it 2–5 existing components working as one unit with a single job?yes → Molecule Q4Otherwise it is indivisible and needs only foundations.→ Atom

The agent states the result and the deciding question. If two answers fit (e.g. a card that could be molecule or organism), it asks the user once and records the answer in the contract.

Composition order the agent must follow

1ReuseAn existing component already does the job
2ConfigureUse its existing props or variants
3ComposeCombine existing components with layout rules
4CreateNew component through Extend, lowest level first

Raw values are never an option. A step is only allowed when the one before it can’t do the job, and the agent states why.

Status lifecycle

DRAFTBuilt by ExtendContract written, built, docs generated
CANDIDATEChecks passingAll QA blockers pass; usable but may change
STABLEConfirmedReviewed by the user or used on 2+ screens
DEPRECATEDReplacedPoints to its replacement; removed later

The status is a property in each contract and is shown in the component description and doc header. Breaking changes to a stable component need a new major version entry in the changelog.

Promotion rule for the “Screen” path

A composition built inside a screen starts as a local component. It enters the library through Extend when it is reused on a second screen, used three or more times on one screen, or the user asks. Example: on a first dashboard, a set of filter tabs used three times is promoted immediately as a molecule; a summary card used once stays local until a second screen needs it.

Recipes are short notes on what a text field, menu or table usually needs, distilled from the reference set through ATM. Extend consults the matching recipe at step 2 so the brief doesn’t miss common states or parts. Recipes are never generated on their own.
05 · Determinism

The generation pipeline

Each stage has typed inputs and outputs written to a ledger. The agent may only decide inside a stage when the spec explicitly lists the choice and its rule.

STAGE 0Brand profileQuestionnaire → validated brand.profile.yaml
STAGE 1DeriveTables → numeric tokens (ramps, radii, heights, type scale, shadows)
STAGE 2TokensVariables, scopes, code syntax, modes
STAGE 3StylesText, effect, grid styles bound to tokens
STAGE 4AtomsBuilt from atom contracts in ID order
STAGE 5Docs + QABlocks generated from contracts; checks run
ANY TIMEExtendNew atom, molecule, organism or template on request, from a design, or from a screen

Rule D1 · No invented values

Any number not produced by a derivation table or listed in a contract is a spec violation. If a value is missing, stop and report, never guess.

Rule D2 · Overrides are data

A user override (e.g. “radius 6”) is written into profile.overrides and flows through the same tables, so it stays reproducible.

Rule D3 · Fixed ordering

Pages, Sections, matrices, properties and doc blocks follow the order in the contract. The agent never re-sorts for aesthetics.

06 · Brand-driven, still agnostic

Brand profile → derivation tables

The spec stays brand-agnostic because it contains tables, not values. The brand fills the profile, and the tables turn the profile into tokens.

# brand.profile.yaml (validated by schemas/brand-profile.schema.yaml)
product:
  name: "<product name>"
  type: saas-app          # saas-app | marketing | mobile | internal-tool
  platforms: [web-desktop, web-responsive]
brand:
  primary: "<brand color hex>"
  accent: null
  neutral_temperature: cool   # cool | neutral | warm | from-primary
  typeface: { ui: "<brand typeface>", mono: "<optional>" }

Color is computed, not picked

Primary hex → OKLCH. An 11-step ramp uses fixed lightness targets (0.98 … 0.25) and a fixed chroma curve, clipped to the sRGB gamut. solid = the first step ≥ 500 whose white text reaches 4.5:1. Neutrals reuse the brand hue with chroma set by temperature. The full table lives in tokens/derivation/color.md.

Component tokens become the default

btn.primary.default.bg.hover aliases a semantic role. Re-branding touches tables, never components. This is the Primitive → Semantic → Component architecture, used by default rather than as an option.

Budgets replace observed counts

Variant totals are a formula over props minus exclusions. QA compares the real count with the formula, so there are no copied numbers to drift.

Measurements live in tables only

The contract never states “40px”. It references size.control.{Size}, whose value comes from the Density row.

09 · Figma build contract

Exactly how every page is built

One canvas recipe for every component page, using Figma SECTION nodes at fixed positions. The same recipe repeats on every page, so every page has the same shape.

Section · Source x=0
Component set (matrix layout)
Private parts .Part/…
Component tokens table
Section · Specs x=+200
Anatomy (generated from layers)
States strip
Sizing & spacing overlay
Section · Guide x=+200
Overview + usage
Do / Don’t pairs
Accessibility
In context (uses parent level)

Sections sit left to right with a fixed 200px gap. Inside each Section, frames stack vertically with a fixed gap from doc.space.section. Doc frames are 1440 wide; the reading column is 720.

Matrix layout algorithm

Columns = the cartesian product of matrix.cols, rows = the product of matrix.rows, both in contract order. Cell size = max variant size in that row or column + doc.space.row. Row and column labels are generated. Same contract → same pixel positions.

Naming grammar

Page 2.1 Button · Set Button · Variant Size=md, Emphasis=primary, … · Private .Part/Button label · Doc frame Doc / 2.1 Button / Anatomy. Layer names come only from layers.

Binding rules

Every fill, stroke, gap, padding, radius, size and text style is bound. Raw values are allowed only inside Foundations/1.8 Brand assets (logos, flags, illustrations), and those must be listed in the asset manifest.

Known engine rules, written into the contract

Spread-based focus rings require clipsContent. resize() resets sizing modes, so set Hug or Fill afterwards. Bound paints ignore paint opacity, so use layer opacity. These lessons from the last build become build steps instead of tribal knowledge.

11 · Quality

QA as executable checks

Each “Fail QA when…” sentence becomes a check with an ID, a Plugin-API assertion and a severity. The agent runs them and reports results; it does not judge.

Q-bind-allEvery fill, stroke, padding, gap, radius and text node on component layers is bound to a variable or style.blocker Q-budgetThe variant count equals variant_budget, and every non-excluded combination exists exactly once.blocker Q-layer-namesThe layer tree matches layers names and order. No default names (Frame 12, Rectangle).blocker Q-scopesNo variable uses ALL_SCOPES, and every variable has WEB code syntax and a description.blocker Q-contrast-aaText/background pairs used by the component meet 4.5:1 (3:1 for large text and icons) in every mode.major Q-focus-visibleA focus variant exists, differs from hover, and renders its ring (clip enabled).major Q-hit-targetInteractive height ≥ size.touch-min on touch platforms.major Q-levelInstances inside the component respect the atomic level rules.major Q-docsEvery block listed in docs exists in the Guide or Specs Section.minor Q-determinismA regenerated token ledger from the same profile is byte-identical to the stored one.minor
