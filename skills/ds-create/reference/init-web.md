# `/ds-create init-web`

Open DS Create Builder BEFORE collecting context or generating foundations. This command finishes when the empty/onboarding Builder is running and opened; the design system's init remains incomplete until its saved draft has been approved, generated and audited in Figma (`reference/init.md`). `init` remains available for chat-led setup. `build` is still separate.

## Launch immediately

Read `workflow/MANAGER.md` for the local lifecycle. For this bootstrap only, defer the global generation specs, questionnaire, brand inputs, Figma readiness and font checks to the local preparation job; do not ask setup questions in chat before opening Builder.

From the selected workspace root, verify Node20+ and run:

```sh
node kit/tools/manager.mjs init-web
```

If the user names a system/session, or the current conversation already identifies the session to resume, supply `--slug {slug}`. With no existing sessions, the command creates an isolated `session-{uuid}` folder without asking for a brand name. If sessions already exist, it returns `action: choose-session`, names/statuses and explicit resume commands; offer those choices plus New session, then run the chosen `--slug` or `--new`. `node kit/tools/manager.mjs sessions` lists sessions read-only. Never silently attach to another system or start an extra empty one when the user intends to resume. Keep this opaque output/session ID and resume command stable. On first Context save, the project name determines a separate inputSlug (Acme Design System → acme-design-system). All subsequent input paths use setup.inputSlug; output paths keep the session ID. Do not attach to another system by guessing from unrelated input folders. Repeating with the same slug reuses its healthy server. Existing initialized systems open normally without first-run onboarding.

Before reporting Builder ready, start or reuse the session's native background worker using `reference/background-worker.md`. It runs the portable listener, keeps its terminal input open, and waits for preparation/Publish events. Install the listener's Node dependencies automatically if absent. No user-managed MCP registration, connection JSON, copy/paste instruction or second chat message is part of setup. Figma is already connected to the launching agent; its worker uses those same authorized tools for a Publish event only. Local preparation does not authorize Figma. Verify the listener's actual listening receipt plus its native heartbeat acknowledgement and fresh agentSeenAt, as well as Builder health. A Node PID without a native agent check-in is unready. If the host has no persistent native background-agent capability, report that bootstrap capability as unavailable; do not pretend a detached Node watcher executes AI work or silently launch a named AI CLI. The server may open for inspection, but automatic processing has not been established.

The return includes actual URL, pid, instance and outputDir. Check `/api/health`, open that URL, verify the Context modal, and report the URL promptly. Leave the detached server running. Do not report a running Builder without health evidence; on failure inspect manager/server.log. Do not generate placeholder tokens, sample brand data, a successful init ledger, or a Figma file just to launch it.

## Setup happens in Builder

The initial modal asks for **Project name**, **Context / Instruction**, and **Context files**. Project name is required (1–100 trimmed single-line characters; spaces and Unicode are allowed). It names the Builder/design system; the actual product described in context may have a different name. Save it as the chosen display name and derive the initial input folder: lowercase kebab case, accent-normalized, Unicode letters/numbers preserved, at most60 characters. Names with no letters/numbers need correction. Keep the saved inputSlug stable on later display-name changes and keep output/session folders and the resume command stable. Either text or at least one file is needed; files are optional when context is provided. Closing it lets the user explore the empty Builder; Context reopens it. No Figma link is required for local preparation.

Submit saves the project name in manager/setup.json and in the context source, and the verbatim context under `workspace/input/{inputSlug}/chat/` and each original file under `workspace/input/{inputSlug}/uploads/{batch-id}/{filename}`. The server stores inputSlug in setup.json and every trusted worker request. An existing unrelated destination folder is a conflict: ask for a different project name instead of merging or adding an invisible suffix. Existing files under this same session’s old input ID are copied intact into its initial named folder, preserving the originals. Legacy already-submitted sessions keep their existing input path. Unique batch paths avoid overwriting existing inputs. Filenames stay intact. Unsupported/unreadable inputs remain listed and the agent asks for a usable version. In questions, blocked/failed and ready states, **Edit context / add files** opens the same form. Save & prepare again explicitly starts a new input revision. Replacing the same filename uses its newest upload while preserving prior original bytes; older answers stay available unless the newest instructions revise them. Stale tabs conflict rather than overwriting a newer context. Stop an active job before editing. Context includes a copyable `ds-create init-web --slug {slug}` command for another chat. Upload limits are10 files,25MB each,50MB total; context is20,000 characters. This storage stays local; the local agent reads it using its existing configured model/provider. Do not promise offline AI processing.

The worker request carries projectName and inputSlug explicitly. Use workspace/input/{inputSlug}/ for inputs, answers and sources, and workspace/output/{slug}/ for outputs; do not infer one from the other. Use it for ledger.system and foundation-plan.projectName and record it as a user decision; do not ask for it again or substitute the opaque session ID. The ready/Publish checks reject a mismatched project identity. Builder header, saved context, resume disclosure and session discovery display the saved name even before generation finishes. Renaming through Edit context makes a new input revision and requires preparation/review again, while old names/sources remain recorded.

A queued MCP preparation is taken by the connected agent, which reads this system's saved inputs and prepares only init's LOCAL stages0–4. It loads `reference/init.md` and its required references, follows the same input precedence, question/YOLO rules, decisions, source manifest and canonical draft schema. It does not restart Builder or proceed into Figma. The request and model output are under manager/setup-jobs/{id}/; manager/setup.json is server/worker-owned state. Do not overwrite it from the agent.

The agent uses the structured MCP handoff, with design questions answered in Builder. Missing/conflicting choices return structured `questions` with unique ids, prompt and optional suggested options; Builder shows them as fields (suggestions allow free text). User answers are saved verbatim in chat and a new bounded continuation reads all prior inputs/answers. Record the settled answers in answers/01-init.md and index every file in sources.md. Do not repeatedly ask answered questions or choose a brand font/color without the user's decision or explicit YOLO. A supplied product description is required even in YOLO. Existing frozen values stay frozen. If baseline data is only accessible through Figma, ask for an export/resolution; this preparation worker has no Figma authorization.

A ready local result requires typed values for every declared mode, compatible cycle-free aliases, usable styles, settled platform, saved decisions/sources/report, and ledger step1 done,2–4 todo with foundationReview pending. Write the source-bound `foundation-plan.json` defined in workflow/MANAGER.md, using the trusted request inputHash/inputRevision; record included names or explicit sourced exclusions for each domain and preserve existing naming. New systems follow Part C semantic aliases, descriptions, explicit scopes/code syntax, hidden raw primitives and collection/token/style naming. The checker has no universal token-count threshold. The web checks these artifacts rather than trusting process exit or the word ready. This is a review handoff, never completed init. Partial drafts during questions/errors/running jobs stay hidden and cannot be published.

The runner snapshots every regular file in the selected input tree, including knowledge and newly added files. Only generated sources.md and answers/01-init.md are excluded. It checks additions, edits and removals before/after preparation and publication; changing source inputs after readiness requires preparing again. Read only this selected tree; loose shared inputs must be assigned/copied into this session by the user, not silently read outside the tracked snapshot. A missing/disconnected MCP client, failed jobs, changed inputs or cancellation leave the input intact with retry/stop guidance. Reload/reopen resumes from saved server state; in-progress text/files not yet submitted stay only in the current page. Stop does not undo files already written. Submitting closes the intake modal and shows persistent task rows, public Activity, saved source cards and required inline questions in Overview. Questions offer clickable suggestions plus custom answers; unsubmitted answer drafts survive reload in the same browser tab. Only Save answers & continue saves them to the workspace. Closing Context leaves the job running. Stage-start messages never prove completion; rows await the existing saved-draft checks. Ready Overview retains a Preparation activity link. The connection owns an exclusive attempt/lease; disconnect or process death marks unfinished preparation Blocked. Viewer restart leaves the MCP client alone. Stop waits for a claimed owner to acknowledge cancellation. Queued work is Waiting for agent with no running spinner; stage/update events come from MCP tools, and only validated artifacts can become Ready. No real agent command or arbitrary filesystem target comes from browser input.


**Basic motion and iconography.** New systems include basic UI motion: durations, easing, delays and Standard/Reduced modes from `specs/foundations/1.6-motion.md`. Excluding animated illustrations or complex/expressive interactions never silently excludes this baseline. Ask only if a source explicitly and ambiguously prohibits UI transitions themselves; retain frozen existing values. Record `motionPolicy: "basic-ui"` in new preparation plans when this baseline applies. Iconography starts with Lucide from the prepared local catalog and the same registry as web docs; record that library choice. Builder presents a local library reference during init, while Figma icon components and full documentation remain a later build step. Existing systems keep their library.

## Review, Figma, build

When local preparation is ready, review foundations in the existing Builder. Controller edits remain unsaved previews. To revise the brief or upload a readable replacement, use Edit context / add files and Save & prepare again, then review the new saved draft. For direct agent edits, retain the same input-bound plan and increment the canonical draft revision; changed source inputs require a new preparation. This onboarding is not a general web chat or a token editor.

Publish → Publish to Figma explicitly approves the saved revision/target and queues the approved continuation for a compatible MCP agent to claim through DS Create MCP. Alternatively provide the file and approval in the user's agent, identifying this session slug. Follow init's Figma readiness, inventory, fonts, generation and audit gates. Init is complete only after both Builder and audited Figma handoffs. Then offer `ds-create build`; never start it automatically.
