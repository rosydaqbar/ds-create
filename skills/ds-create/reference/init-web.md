# `/ds-create init-web`

Start DS Create Builder BEFORE collecting context or generating foundations. This command finishes when the empty/onboarding Builder is running and its link has been given to the user; the design system's init remains incomplete until its saved draft has been approved, generated and audited in Figma (`reference/init.md`). `init` remains available for chat-led setup. `build` is still separate.

## Launch immediately

For bootstrap read this launch contract and `background-worker.md` only. Defer the full `workflow/MANAGER.md`, global generation specs, questionnaire, brand inputs, Figma readiness and font checks to their actual stages; do not ask setup questions in chat before providing the Builder link.

From the selected workspace root, verify Node20+ and run:

```sh
node kit/manager/cli.mjs init-web --fast-mode
```

If the user names a system/session, or the current conversation already identifies the session to resume, supply `--slug {slug}`. With no existing sessions, the command creates an isolated `session-{uuid}` folder without asking for a brand name. If sessions already exist, it returns `action: choose-session`, names/statuses and explicit resume commands; offer those choices plus New session, then run the chosen `--slug` or `--new`. `node kit/manager/cli.mjs sessions` lists sessions read-only. Never silently attach to another system or start an extra empty one when the user intends to resume. Keep this opaque output/session ID and resume command stable. On first Context save, the project name determines a separate inputSlug (Acme Design System → acme-design-system). All subsequent input paths use setup.inputSlug; output paths keep the session ID. Do not attach to another system by guessing from unrelated input folders. Repeating with the same slug reuses its healthy server. Existing initialized systems open normally without first-run onboarding.

Figma is part of every session unless the user turns it off. Pass `--no-figma` when they say the system should not use Figma; it writes `flags.figma: false` to the session's ledger. The Context dialog's **Use Figma** switch changes the same setting later. With Figma off, Builder hides Publish to Figma and the sync list, and nothing reads or writes Figma.

Next, connect the preparation delivery described in `reference/background-worker.md`. Use the standard pending-tool handoff: `ds_create_wait` through the connected DS Create MCP (also exposed as `ds_create_prepare_wait`; or `node kit/manager/cli.mjs mcp ds_create_wait --json '{"session":"{slug}"}'` when this session has no `ds_create_*` tools; never ask for a restart, see `background-worker.md`, *Without DS Create MCP tools*), or `node kit/manager/cli.mjs wait --slug {slug}` inside a pending terminal tool request. Node waits without model requests; the tool result resumes this main instance when Prepare foundations is submitted. Do not end the agent turn while promising automatic delivery, and do not substitute a detached stdout/notification relay: an active-turn probe does not establish an idle-chat wake. No native subagent, agent/IDE CLI, vendor endpoint or idle AI heartbeat/polling. Host cancellation/timeout detaches this receiver; reattach through the tool lifecycle rather than promising that an ended request is still listening. No source preparation, Figma or build is triggered by startup.

The return includes actual URL, pid, instance and outputDir. Verify `/api/health` and promptly give the user the URL in commentary so they can open Builder and fill the form themselves. Do not open or automate the browser, attach a debugger, or create a tab group. Health confirms the server only; do not claim the Context modal or rendered UI was verified. Then keep the receiving tool call pending for at most five minutes; the model does no work while Node waits. A `wait-expired` result ends this turn without automatically rearming; Builder highlights its disconnected state and offers a short continuation prompt using the same saved session. On its event result, this main instance claims its current attempt and follows the local preparation contract. End the main agent turn after finishing, five-minute wait expiration, host timeout/cancellation or an explicit stop; an idle-chat wake is not part of this portable protocol. Do not generate sample tokens, a successful init ledger or a Figma file merely to launch it.

## Setup happens in Builder

The intake has two steps using the existing Builder controls. **1. General** asks for **Project name**, **Context / Instruction**, and **Context files**, listing selected/saved files without claiming they have been read. Next validates locally and starts no job; Back preserves entries and files. **2. Interface details** selects Light/Dark (one or both), devices/platforms from Questionnaire §1, and explains current documentation tokenization support: Tailwind for Web docs; React Native, Swift and Kotlin token references for App docs. It asks no naming question for a new system; Keep existing naming / Normalize applies only after the context identifies an existing library, through the normal missing-answer handoff (Questionnaire §9). New systems use the fixed canonical architecture; existing frozen values remain protected. Fonts, colors, product details and baseline identity come from context/files. Only Prepare foundations submits both steps. The server validates and saves interfaceDetails with the verbatim context and in the source snapshot, restores them for edits, and passes them to the worker as explicit user choices. All web requests enforce `fastMode:true` and the existing `--fast-mode` Manager FAST workflow; the browser cannot switch to Default or choose a model/provider. Older saved sessions remain readable and revisions retain their selections. Project name is required (1–100 trimmed single-line characters; spaces and Unicode are allowed). It names the Builder/design system; the actual product described in context may have a different name. Save it as the chosen display name and derive the initial input folder: lowercase kebab case, accent-normalized, Unicode letters/numbers preserved, at most60 characters. Names with no letters/numbers need correction. Keep the saved inputSlug stable on later display-name changes and keep output/session folders and the resume command stable. Either text or at least one file is needed; files are optional when context is provided. Closing it lets the user explore the empty Builder; Context reopens it. No Figma link is required for local preparation.

Submit saves the project name in manager/setup.json and in the context source, and the verbatim context under `workspace/input/{inputSlug}/chat/` and each original file under `workspace/input/{inputSlug}/uploads/{batch-id}/{filename}`. The server stores inputSlug in setup.json and every trusted worker request. An existing unrelated destination folder is a conflict: ask for a different project name instead of merging or adding an invisible suffix. Existing files under this same session’s old input ID are copied intact into its initial named folder, preserving the originals. Legacy already-submitted sessions keep their existing input path. Unique batch paths avoid overwriting existing inputs. Filenames stay intact. Unsupported/unreadable inputs remain listed and the agent asks for a usable version. In questions, blocked/failed and ready states, **Edit context / add files** opens the same form. Save & prepare again explicitly starts a new input revision. Replacing the same filename uses its newest upload while preserving prior original bytes; older answers stay available unless the newest instructions revise them. Stale tabs conflict rather than overwriting a newer context. Stop an active job before editing. Context includes a copyable `ds-create init-web --slug {slug}` command for another chat. Upload limits are10 files,25MB each,50MB total; context is20,000 characters. This storage stays local; the local agent reads it using its existing configured model/provider. Do not promise offline AI processing.

The worker request carries projectName and inputSlug explicitly. Use workspace/input/{inputSlug}/ for inputs, answers and sources, and workspace/output/{slug}/ for outputs; do not infer one from the other. Use it for ledger.system and foundation-plan.projectName and record it as a user decision; do not ask for it again or substitute the opaque session ID. The ready/Publish checks reject a mismatched project identity. Builder header, saved context, resume disclosure and session discovery display the saved name even before generation finishes. Renaming through Edit context makes a new input revision and requires preparation/review again, while old names/sources remain recorded.

A queued preparation is taken by the main agent after Node event delivery and stops at init's LOCAL foundation review. New requests use preparationVersion:2 and the complete stage-specific `reference/manager-preparation.md` contract: read the server's extracted source pack, inspect flagged sources, resolve a decisions.json, then invoke the owned local compiler. This replaces the global generation/init read set for this local job. The compiler writes the canonical draft/plan and review artifacts; source precedence, question/YOLO rules and existing proof checks still apply. Legacy saved requests retain their original local init contract. No Builder restart or Figma work. Job artifacts stay under manager/setup-jobs/{id}/; manager/setup.json is server/worker-owned state.

The agent uses the structured MCP handoff, with design questions answered in Builder. Missing/conflicting choices return structured `questions` with unique ids, prompt and optional suggested options; Builder shows them as fields (suggestions allow free text). User answers are saved verbatim in chat and a new bounded continuation reads all prior inputs/answers. Record the settled answers in answers/01-init.md and index every file in sources.md. Do not repeatedly ask answered questions or choose a brand font/color without the user's decision or explicit YOLO. A supplied product description is required even in YOLO. Existing frozen values stay frozen. If baseline data is only accessible through Figma, ask for an export/resolution; this preparation worker has no Figma authorization.

A ready local result requires typed values for every declared mode, compatible cycle-free aliases, usable styles, settled platform, saved decisions/sources/report, and ledger step1 done,2–4 todo with foundationReview pending. Write the source-bound `foundation-plan.json` defined in workflow/MANAGER.md, using the trusted request inputHash/inputRevision; record included names or explicit sourced exclusions for each domain and preserve existing naming. New systems follow Part C semantic aliases, descriptions, explicit scopes/code syntax, hidden raw primitives and collection/token/style naming. The checker has no universal token-count threshold. The web checks these artifacts rather than trusting process exit or the word ready. This is a review handoff, never completed init. Partial drafts during questions/errors/running jobs stay hidden and cannot be published.

The runner snapshots every regular file in the selected input tree plus shared regular files directly in workspace/input/. Root files are read in place and identified as ../{filename} relative to the selected folder; the repository root README.md and OS .DS_Store are excluded, as are selected-tree generated sources.md and answers/01-init.md. Other system folders are never traversed. Builder lists discovered root files as workspace inputs and accepts them without a redundant upload or placeholder context. It checks additions, edits and removals before/after preparation and publication; changing source inputs after readiness requires preparing again. Read every trusted snapshot entry before asking missing questions, resolving listed ../{filename} entries only to direct workspace/input/ files. Preserve the original files and exact source keys. No other parent path or other system folder is authorized. A missing/disconnected MCP client, failed jobs, changed inputs or cancellation leave the input intact with retry/stop guidance. Reload/reopen resumes from saved server state; in-progress text/files not yet submitted stay only in the current page. Stop does not undo files already written. Submitting closes the intake modal and shows persistent task rows, public Activity, saved source cards and required inline questions in Overview. Questions offer clickable suggestions plus custom answers; unsubmitted answer drafts survive reload in the same browser tab. Only Save answers & continue saves them to the workspace. Closing Context leaves the job running. Stage-start messages never prove completion; rows await the existing saved-draft checks. Ready Overview retains a Preparation activity link. The connection owns an exclusive attempt/lease; disconnect or process death marks unfinished preparation Blocked. Viewer restart leaves the MCP client alone. Stop waits for a claimed owner to acknowledge cancellation. Queued work is Waiting for agent with no running spinner; stage/update events come from MCP tools, and only validated artifacts can become Ready. No real agent command or arbitrary filesystem target comes from browser input.


**Basic motion and iconography.** New systems include basic UI motion: durations, easing, delays and Standard/Reduced modes from `specs/foundations/1.6-motion.md`. Excluding animated illustrations or complex/expressive interactions never silently excludes this baseline. Ask only if a source explicitly and ambiguously prohibits UI transitions themselves; retain frozen existing values. Record `motionPolicy: "basic-ui"` in new preparation plans when this baseline applies. Iconography starts with Lucide from the prepared local catalog and the same registry as web docs; record that library choice. Builder presents a local library reference during init, while Figma icon components and full documentation remain a later build step. Existing systems keep their library.

## Review, Figma, build

When local preparation is ready, review foundations in the existing Builder. Controller edits remain unsaved previews. To revise the brief or upload a readable replacement, use Edit context / add files and Save & prepare again, then review the new saved draft. For direct agent edits, retain the same input-bound plan and increment the canonical draft revision; changed source inputs require a new preparation. This onboarding is not a general web chat or a token editor.

After a ready finish, hold `ds_create_wait` again so the Publish click reaches this agent. When the user approves in chat instead, queue it yourself with `node kit/manager/cli.mjs publish --slug {slug}` and claim it (`SKILL.md` rule 15). Publish → Publish to Figma explicitly approves the saved revision/target and queues the approved continuation; the pending wait returns it as `publish-request`, claimed with `ds_create_publish` (`publish-mcp.md`). Its first step is the blocking font check; missing fonts are resolved by the user in the Publish dialog. On resume (`ds-create init-web --slug {slug}`), check both `ds_create_prepare_status` and `ds_create_publish_status` and claim whichever request is queued. Alternatively provide the file and approval in the user's agent, identifying this session slug. Follow init's Figma readiness, inventory, fonts, generation and audit gates. Init is complete only after both Builder and audited Figma handoffs. Then offer `ds-create build`; never start it automatically.
