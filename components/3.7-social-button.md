# 3.7 Social button

Social buttons let people sign in or sign up with a third-party account. A **Social button** is a Button (2.1) with the provider's mark and a "Sign in with …" label; a **Social button group** stacks or lines up several of them for a sign-in screen.

Use them only for authentication and account linking. Use a normal Button for every other action, and the app-store badges on 1.8 Brand assets for app downloads.

# 3. Composition

| Part | From | What the Social button sets |
| --- | --- | --- |
| `Button` | 2.1 Button | `Emphasis=secondary`, `Size` (md → md, lg → lg), `State`, `Icon only` (same value as the Social button); leading icon swapped to the Social mark; label "Sign in with {Provider}" (hidden when `Icon only=true`) |
| `Social mark` | 1.8 Brand assets | `Provider` as the button; `Mono=true` for `Type=mono` |

The Social button keeps the Button's anatomy, including the **Text padding** optical wrapper, so a Social button and a Button of the same size line up exactly in one column.

# 4. Social button

## Properties

| Property | Type | Values | Default |
| --- | --- | --- | --- |
| `Size` | variant | `md, lg` | `lg` |
| `Provider` | variant | the providers chosen at initiation (six by default) | first provider |
| `Type` | variant | `solid, color, mono` | `color` |
| `Icon only` | variant | `false, true` | `false` |
| `State` | variant | `rest, hover, focus` | `rest` |

Variants: 2 × 6 × 3 × 2 × 3 = **216** with six providers.

## Type

| Type | Fill and border | Mark | Label |
| --- | --- | --- | --- |
| `solid` | the provider's own fill (`social-button/{provider}/fill`), no border | the mark version for the provider's solid background | `social-button/{provider}/fg` |
| `color` | secondary Button: `color/surface/base`, `color/border/default` | full-colour mark (`Mono=false`) | `color/text/secondary` |
| `mono` | secondary Button | single-colour mark (`Mono=true`), follows `color/icon/secondary` | `color/text/secondary` |

`solid` overrides the Button instance's fill and label colour with the provider's component tokens. These tokens hold the provider's official colours and stay the same in every colour mode. The label still reaches 4.5:1 on the provider fill, so `fg` is the provider's own light or dark colour that passes, not always white (Guidelines topic 6).

## Anatomy

```text
Social button (Icon only=false)
└─ Button                        2.1, Emphasis=secondary, Fill width in layouts
   ├─ Leading icon               Social mark (1.8), size/icon/md (lg: size/icon/lg)
   ├─ Text padding               Button's optical wrapper
   │  └─ Label                   "Sign in with {Provider}"
   └─ (trailing icon off)

Social button (Icon only=true)
└─ Button                        2.1, Emphasis=secondary, Icon only=true
   └─ Leading icon               Social mark (1.8)
```

- The mark is centred in its icon box and keeps its official proportions; it is never redrawn, recoloured (except the mono version) or rebuilt from text.
- In layouts, text Social buttons are set to Fill so every provider button in a column has the same width, with the content centred.

## Sizes and measurements

| Size | Height | Padding x | Gap | Mark | Text style |
| --- | --- | --- | --- | --- | --- |
| `md` | `size/control/md` = 40 | `button/padding-x/md` = 14 | `space/xs` = 4 + optical 2 | `size/icon/md` = 20 | `type/body/sm/semibold` |
| `lg` | `size/control/lg` = 44 | `button/padding-x/lg` = 16 | `space/sm` = 6 + optical 2 | `size/icon/lg` = 24 | `type/body/md/semibold` |

These values come from Button (2.1). Icon-only Social buttons use Button's own `Icon only=true` form, so they are square at the same control height (40 at `md`, 44 at `lg`) and line up with text Social buttons and other buttons in the row. Icon button (2.2) is not used here: it is the compact utility control and is smaller than a control. The mark is one icon step larger at `lg` so provider marks read clearly.

## States

| State | `solid` | `color`, `mono` |
| --- | --- | --- |
| `rest` | provider fill | Button secondary rest |
| `hover` | `social-button/{provider}/fill/hover` | Button secondary hover; mono mark moves to `color/icon/primary` |
| `focus` | `focus/default` ring | Button secondary focus |

Social buttons have no disabled state: if a provider is unavailable, remove its button.

# 5. Social button group

| Property | Type | Values | Default |
| --- | --- | --- | --- |
| `Size` | variant | `md, lg` | `lg` |
| `Icon only` | variant | `false, true` | `false` |
| `Type` | variant | `solid, color, mono` | `color` |

Variants: 2 × 2 × 3 = **12**. The buttons inside are exposed nested instances, so designers pick the providers without detaching.

```text
Social button group (Icon only=false)
layout: Vertical, gap space/lg, width Fixed 360 in the set (Fill in layouts)
├─ Social button                 Fill width
├─ Social button                 Fill width
└─ Social button                 Fill width

Social button group (Icon only=true)
layout: Horizontal, gap space/lg, Hug (or Fill with equal-width buttons)
├─ Social button × 3–6           Icon only=true
```

Default content: the first three providers in the text group; the first four in the icon-only group. Every button in a group has the group's `Size` and `Type`.

# 6. Matrix layout

- `Social button`: one block per `Type`; inside, columns `State` → `Icon only`, rows `Provider` → `Size`.
- `Social button group`: columns `Icon only`, rows `Type` → `Size`.
- Do not collapse the 216-variant matrix into a few samples.

# 7. Guidelines

Topics in `3.7 Social button · Guidelines`, in order, each with a visual built from real instances:

1. **When to use.** A sign-in card with social buttons, next to a normal form action. Caption: "Social buttons are for signing in with another account, nothing else."
2. **Three treatments.** One provider in `solid`, `color` and `mono` side by side. Caption: "Pick one treatment per screen; follow each provider's own brand rules."
3. **Text or icon only.** A stacked text group and an icon-only row. Caption: "Use text buttons when there is room; icon-only rows only for well-known providers, with accessible names."
4. **Alignment with other buttons.** A primary "Sign in" Button and a Social button of the same size in one column, with a guide on the shared height and label position.
5. **Content.** "Sign in with {Provider}" on sign-in screens, "Sign up with {Provider}" on sign-up, "Continue with {Provider}" when the same screen does both. Use the provider's name exactly as they write it.
6. **Accessibility.** Icon-only buttons are named "Sign in with {Provider}"; the mark is decorative inside a text button. Focus rings follow the Button.
   - On `solid`, the label and the mark reach 4.5:1 on the provider fill and its hover. Where white on the provider colour fails, use the provider's own dark brand colour instead. GitLab: white on GitLab orange `#FC6D26` is 2.85:1, so the label and mark use GitLab charcoal `#171321`.
   - Facebook is the one accepted exception: white on `#1877F2` is 4.23:1, and Facebook's brand rules fix both colours. Keep it, and say on the page that it is a documented exception. Visual: the GitLab and Facebook solid buttons with their ratios and a pass or exception badge.
7. **Do / don't** (`Doc/Do-dont` pairs):
   - Do use the provider's mark from 1.8. Don't rebuild a mark from text or a generic icon.
   - Do keep one treatment in a group. Don't mix solid and mono buttons.
   - Do give text buttons equal widths. Don't let widths follow label length.
   - Don't use a social button for actions other than signing in or linking an account.
8. **Maintenance.** Button shape, sizes and focus come from Button (2.1); marks come from 1.8; provider colours live in the `social-button/*` tokens.

# 8. QA

Fail QA when:
- a Social button is a drawn frame instead of a Button instance, or the icon-only form uses Icon button (2.2) instead of `Button, Icon only=true`;
- the Text padding wrapper is missing;
- the mark is redrawn, stretched or off-centre, or is a generic icon;
- `solid` colours are hard-coded instead of `social-button/{provider}/*` tokens;
- group rows are detached copies instead of Social button instances;
- buttons in one group have different sizes or treatments;
- the 216-variant matrix is reduced to a showcase;
- a `solid` label or mark is below 4.5:1 on its provider fill (rest or hover), other than the documented Facebook exception;
- when offered, GitLab `solid` uses white instead of GitLab charcoal `#171321`, or the Facebook exception is not documented on the page.
