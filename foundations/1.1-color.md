# 1.1 Color

The Color page shows the whole color system: the raw palettes, the gradients, and every semantic color role with its value in each mode and what it is for. It is a wide, multi-frame canvas. Never reduce it to one palette grid or squeeze it into one fixed canvas size.

Color works in two layers:

```text
Primitives (palette/*)      the raw palette, hidden from pickers
        ↓ aliases
Color collection (color/*)  semantic roles with one value per mode (Light, Dark, …)
        ↓ bindings
Components
```

Components bind `color/*` roles, never `palette/*` primitives.

## .Main

- `.Main/Color gradient card`: a gradient specimen (size `doc/measure/specimen`, radius `doc/radius/surface`, subtle border) above the style name and its stops.
- Standard swatches use `Doc/Color swatch` from `9.1 Doc kit`; no separate swatch helper is made.

## · Overview

Sections in this order. Every section starts with a `Doc/Block note`; every row is `Doc/Row note` (left, `doc/measure/row-note`) → swatches (right, filling the rest, growing the frame when the family is long).

### 1. Base colors

Block note: `Base colors`, badge `Primitives`.

| Row | Swatches | Notes |
| --- | --- | --- |
| `Base` | `palette/base/white`, `palette/base/black`, `palette/base/transparent` | transparent shows a checkerboard behind the specimen |
| `Brand` | the full `palette/brand/*` scale | badge `Brand`; row note says which step is the main action color (`600` by default) |
| `Alpha` | `palette/alpha-black/*` on a light surface, `palette/alpha-white/*` on a dark surface | used for overlays, shadows and transparent neutrals; row note says where they are used |

### 2. Extended palettes

Block note: `Extended palettes`, badge `Primitives`. Short description: the families the product uses, and which family serves each status.

One row per family, in this order:
1. `Neutral` (`palette/neutral/*`), badge `Neutral`.
2. The danger family, badge `Danger` (red by default).
3. The warning family, badge `Warning` (amber by default).
4. The success family, badge `Success` (green by default).
5. The info family, badge `Info` (blue by default).
6. Supporting families, each with a one-line usage note in its row note (for example "Charts and categorical tags only").

Naming: `brand` and `neutral` are named by role so the brand can change without renaming anything. Every other family is named by hue: `palette/red/*`, `palette/amber/*`, `palette/green/*`, `palette/blue/*`, `palette/sky/*`, and so on. Status badges show which hue serves which status.

The page can present any of these hue families:

```text
Red · Orange · Amber · Yellow · Lime · Green · Emerald · Teal · Cyan · Sky · Blue · Indigo · Violet · Purple · Fuchsia · Pink · Rose · Slate · Gray · Zinc · Neutral · Stone · Taupe · Mauve · Mist · Olive
```

This list shows what the page supports. It is not a list to generate. Build only the families the product uses (see Guidelines, *Defining the color palette*).

Default steps per family: `50, 100, 200, 300, 400, 500, 600, 700, 800, 900, 950` (11 steps). An existing brand keeps its own steps.

Rules:
- Keep an existing brand palette. Do not regenerate it.
- Every family shown has a product purpose written in its row note.
- Large palettes widen the swatch region. Do not shrink swatches to fit.

### 3. Gradients

Block note: `Gradients`, badge `Styles`. Gradients are paint styles, because variables cannot hold gradients.

| Row | Styles |
| --- | --- |
| `Neutral gradients` | `color/gradient/neutral-{n}`: soft neutral fades for empty states and image overlays |
| `Brand gradients` | `color/gradient/brand` (always), then `color/gradient/brand-{n}` |
| `Linear gradients` | `color/gradient/linear-{n}`: multi-hue linear blends from the extended palettes |
| `Mesh gradients` | `color/gradient/mesh-{n}`: image-fill styles for hero and marketing surfaces |

Each gradient is a `.Main/Color gradient card` instance. Each gradient stop is bound to a `palette/*` variable, and the card lists the stop names under the specimen. Build only the groups the brand uses; `color/gradient/brand` always exists.

### Swatch anatomy

Every swatch is a `Doc/Color swatch`:

```text
Doc/Color swatch
├─ Specimen          fill bound to the palette variable
│  └─ Contrast       e.g. "AAA 15.6": the better of contrast against palette/base/white and palette/base/black, written in that color on the specimen
└─ Content
   ├─ Step           e.g. 600
   └─ Value          hex, secondary
```

- All swatches in one family have the same size (`doc/measure/specimen`).
- The specimen is bound to its variable. A hex string is never the specimen, and colored hex text is never a swatch.
- A card like `Crimson Red / #DC143C / Primary identity` with no filled specimen fails QA.

### 5. Fill — `color/fill`

Block note: fills of interactive and status elements: buttons, badges, checkboxes, switches, selected rows.

Every tone (`neutral`, `brand`, `danger`, `warning`, `success`, `info`) has two emphases, `subtle` and `solid`. The parent row is the rest value; its children are the states:

```text
color/fill/brand/solid              rest
├── hover
├── pressed
├── selected
└── disabled
```

Default aliases, where `{hue}` is the family serving the tone (`brand`, `red`, `amber`, `green`, `blue`):

| Name | Light | Dark | Usage |
| --- | --- | --- | --- |
| `color/fill/{tone}/solid` | `{hue}/600` | `{hue}/600` | Solid tone fill: primary buttons, solid badges, checked checkboxes, switch on. |
| ├ `hover` | `{hue}/700` | `{hue}/700` | The solid fill under the pointer. |
| ├ `pressed` | `{hue}/800` | `{hue}/800` | The solid fill while pressed. |
| ├ `selected` | `{hue}/700` | `{hue}/700` | A selected solid item, such as the active segment of a segmented control. |
| └ `disabled` | `neutral/100` | `neutral/800` | Solid fills of disabled controls. |
| `color/fill/{tone}/subtle` | `{hue}/50` | `{hue}/950` | Tinted tone fill: subtle badges, tinted buttons, alert backgrounds. |
| ├ `hover` | `{hue}/100` | `{hue}/900` | The tinted fill under the pointer. |
| ├ `pressed` | `{hue}/200` | `{hue}/800` | The tinted fill while pressed. |
| ├ `selected` | `{hue}/100` | `{hue}/900` | Selected rows and selected menu items. |
| └ `disabled` | `neutral/50` | `neutral/900` | Tinted fills of disabled controls. |

Solid states carry `color/text/on-solid` and `color/icon/on-solid`, so they move **darker** than the rest step in every mode (hover and selected one step, pressed two), never lighter in Dark. A state that must move lighter changes its text role with it. Guidelines topic 5 has the check.

The neutral tone uses its own steps: `solid` rest `neutral/900` / `neutral/50` (hover `800`/`100`, pressed `700`/`200`, selected `800`/`100`), `subtle` rest `neutral/50` / `neutral/900` (hover `100`/`800`, pressed `200`/`700`, selected `100`/`800`). The neutral solid fill is the inverted surface: like `color/surface/inverse`, it flips between modes, so content on it uses `color/text/inverse` and `color/icon/inverse`, never the on-solid roles.

The table on the page lists every tone in full, one tree per tone and emphasis, in tone order neutral → brand → danger → warning → success → info, solid before subtle. Usage copy names the concrete elements for that tone (for example `color/fill/danger/solid`: "Danger buttons and destructive confirmations").

Special fills, after the tone trees:

| Name | Light | Dark | Usage |
| --- | --- | --- | --- |
| `color/fill/none` | `base/transparent` | `base/transparent` | Transparent fill that keeps a layer bound, such as a ghost button at rest. |
| `color/fill/neutral/track` | `neutral/200` | `neutral/800` | Unfilled tracks: progress bars, sliders and the off state of switches. |

## · Guidelines

Topics in this order. Each topic is heading → explanation → visual example → caption. The visual example sits right after its text, is built from this system's own variables and components, and uses the real token names.

### 1. Defining the color palette

Build the palette as a set of roles, not a collection of attractive swatches. A product typically needs:
- **neutral colors** for text, borders, surfaces, dividers, disabled states and structure;
- **brand colors** for primary emphasis, interactive states, links, selected states and branded surfaces;
- **supporting colors** only when the product needs more categories, data visualization or secondary emphasis;
- **feedback colors**: danger, warning, success and info, when those states exist in the product.

Do not add palette families to make the page look complete. Every family needs a written product purpose.

Each family's range must cover subtle surfaces, borders, icons, text, solid fills, and hover, pressed and focus states. Eleven steps (`50` to `950`) cover all of these. An existing palette keeps its own steps.

**Visual: palette system overview.** One large specimen grouping the neutral, brand, feedback and supporting families. For each family: the tonal ramp, the primitive names, the hex values and contrast annotations. The point is to see the whole palette architecture at a glance. Leave out any family the product does not use.

### 2. Choosing additional colors

Add a color family only when it solves a real interface need. Before adding one, decide:
1. what product role it serves;
2. which steps are actually needed;
3. whether it needs icon, border, surface or solid treatments;
4. whether it must work in every color mode;
5. whether its important text and background pairs meet the accessibility target.

Do not add decorative palettes with no product use. When the system already has approved supporting palettes, keep and audit them instead of replacing them.

**Visual: adding a family.** A new family row (for example `palette/teal/*`) shown next to the `color/category/teal` roles it feeds and one tag and one chart series that use them, so the purpose is visible before the family is added.

### 3. Define the color system before component work

Set up primitives and semantic roles before building or rebuilding large component families:

```text
Primitive palette  →  Semantic color roles  →  Component usage
```

Components bind semantic roles, not primitives:

```text
palette/brand/600  →  color/fill/brand/solid  →  Button · Emphasis=primary, Tone=brand, State=rest
```

Because components only know the role, the brand palette can change while what every component means stays the same.

When auditing an existing system:
- find raw color values used directly in components;
- group repeated purposes into semantic roles;
- keep intentional exceptions and document them;
- do not rename or restructure unless the chosen action allows it.

**Visual: raw color vs system color.** One realistic component (a date picker, form field, card or segmented control) shown twice. *Before*: every layer uses a raw hex value. *After*: the same layers bound to `color/*` roles. Callouts on three layers show the raw value, the semantic role and the primitive it resolves to.

**Visual: primitive → semantic → component.** A three-column diagram with connector lines:

```text
Primitives            Semantic roles            Components
palette/neutral/900 → color/text/primary      → Text field label
palette/neutral/700 → color/text/secondary    → Text field hint
palette/brand/600   → color/fill/brand/solid  → Button
palette/red/600     → color/border/danger     → Text field (Status=invalid)
```

Each primitive is a swatch, each role is a `Doc/Token badge` with its swatch, each component is a real instance.

### 4. Color accessibility

Check accessibility while you build the palette and the semantic mappings, not after the components are done.

Test the roles that matter:
- primary and secondary text;
- links;
- button labels;
- form labels;
- placeholders (they reach 4.5:1 like body text);
- icons that carry meaning;
- borders that identify controls;
- focus indicators;
- text on brand surfaces;
- danger, warning and success content;
- disabled states (exempt from contrast rules but still visible as present).

Color is never the only carrier of meaning. When a state carries important information, pair the color with text, an icon, a shape change, a supporting message, and the right state in code.

**Visual: contrast in context.** Built from real surfaces and components, not loose rectangles: a passing pair (`color/text/secondary` on `color/surface/base`), a weak pair (`color/text/placeholder` at the mid-gray step on `color/surface/sunken`, next to the step that fixes it), and an error field with icon and message. Each pair shows its ratio, its level badge (AAA, AA, AA large, fail) and the two token names.

### 5. Contrast requirements and testing

State the accessibility target the product uses (WCAG AA by default: 4.5:1 for body text, 3:1 for large text and for UI parts such as control borders and icons). Test real semantic pairs, not primitives on their own: a step that passes on one surface can fail on another.

Test at least these pairs, in every mode:

```text
color/text/primary              on color/surface/base
color/text/secondary            on color/surface/base
color/text/secondary            on color/surface/sunken
color/text/primary/on-brand     on color/surface/brand-solid
color/text/on-solid             on color/fill/brand/solid
color/text/danger               on color/fill/danger/subtle
color/border/default            on color/surface/base   (when the border is the only thing that shows a control)
color/border/focus              on color/surface/base and color/surface/raised
```

The full list is the *Contrast pairs* checklist in QA. These rules prevent the failures that show up most often:
- **Placeholder text is read, so it is text.** `color/text/placeholder` reaches 4.5:1 on `surface/base`, `surface/raised`, `surface/sunken` and `surface/overlay` in every mode. The usual failure is the mid-gray step in both modes: it fails on the dark surfaces. Move it toward the ink end in Light and toward the light end in Dark until every surface passes.
- **States under on-solid text move darker.** Every solid fill that carries `color/text/on-solid` (brand and danger by default, and any other tone used that way) keeps the text at 4.5:1 in rest, hover, pressed and selected, in every mode. Hover and selected go one step darker, pressed two. A Dark state that goes lighter under white text fails; if a state has to go lighter, its text role changes with it. Check each state, not only rest.
- **Tone text on its own tint, in every state it's drawn on.** `color/text/{danger, warning, success, info, brand}` reaches 4.5:1 on `color/fill/{tone}/subtle` and its `hover` state in every mode (badges, tags, banners). The action tones (brand and danger: secondary and tertiary buttons, selectable rows) also pass on `pressed` and `selected`. The subtle states get stronger as they go: in Light the pressed tint is darker, so the text often needs one step darker (`800`); in Dark the hover and pressed tints are lighter, so the text needs the lighter step (`300`, sometimes `200` for danger on pressed). Test each state, not only rest.
- **The neutral solid is inverted.** `color/fill/neutral/solid` pairs with `color/text/inverse` and `color/icon/inverse`. On-solid white on it fails in Dark.

Automated checks help, but also show in-context examples, because:
- alpha colors depend on the surface below them;
- tinted surfaces change the result;
- disabled states can become too faint to notice;
- nested and raised surfaces create pairs the palette row never shows.

**Visual: tested pairs.** A grid with one row per pair above: text sample on its real surface, the two token badges, the ratio and a pass or fail badge, one column per mode. A failing pair shows the fix next to it (the step it moved to).

### 6. Managing colors through variables

The color architecture makes system-wide changes possible from one place:

```text
Primitive values  →  Semantic aliases  →  Component bindings
```

- Primitives hold the raw palette.
- Semantic variables describe intent.
- Components bind semantic roles wherever possible.

When a primitive changes:
1. update the value in `Primitives`;
2. review the semantic aliases that point at it;
3. let the change flow into components;
4. check affected states and real product screens;
5. run the contrast tests again (topic 5).

Never recolor individual components when what they mean has not changed. Documentation always shows this system's own collection, mode and token names.

**Visual: editing workflow.** Built from this file's own variables, as five steps with arrows:
1. the `Primitives` collection open, `palette/brand/600` selected;
2. the `Color` collection with its `Light` and `Dark` modes;
3. the edited primitive value (old swatch → new swatch);
4. the semantic roles that alias it (`color/fill/brand/solid`, `color/border/brand`, `color/text/brand`) with their new swatches;
5. a primary button, a link and a selected checkbox updated.

### 7. Changing the brand palette

Change the brand at the primitive layer, never component by component. Review the whole brand family:
- subtle brand surfaces;
- borders;
- brand icons and text;
- solid action fills;
- hover and pressed states;
- selected states;
- text on brand surfaces;
- the mapping in every mode.

Keep semantic roles the same when their purpose has not changed.

After updating the brand primitives, check primary and secondary actions, links and selected states, the focus ring (it uses the brand family by default), the contrast of every brand role, and each mode on its own. A brand change is done only when the whole family and its mappings pass.

**Visual: brand replacement.** Before and after, with structure, token names and copy unchanged and only `palette/brand/*` replaced. Show the old ramp, the new ramp, and the same primary button, selected tab, checked checkbox and focused input after the change.

### 8. Changing the neutral palette

Neutrals make up most of an interface and set much of its character. A neutral family can be warm, cool, very desaturated, slightly brand-tinted, or high-contrast. There is no single correct gray.

To change the neutral direction:
1. update the `palette/neutral/*` values;
2. keep semantic roles where their purpose has not changed;
3. check the text hierarchy;
4. check that borders and dividers stay visible;
5. check disabled states;
6. check page, card and raised surfaces;
7. check overlays and the dark mode;
8. run the contrast tests again.

Keep an approved existing neutral palette unless the user asks to rebuild it.

**Visual: neutral character.** Three copies of the same small composition (a card with a heading, supporting text, a divider, a text field and a secondary button): desaturated, cool-tinted and warm-tinted neutrals. Brand color and anatomy stay the same. Callouts show how the neutral changes text, borders, surfaces and the overall feel. The direction the system uses is marked `Selected`.

**Visual: neutral update.** Before and after: old neutral ramp, new ramp, the same semantic roles and the same examples, covering at least page background, card surface, primary and secondary text, a divider and a disabled control.

### 9. Updating color-dependent effects

A palette change also reaches shadows, focus rings, overlays and any tinted elevation. Keep these dependencies central:
- shadows use `color/shadow/*`;
- focus rings use `color/border/focus` and `color/border/danger`;
- the scrim uses `color/overlay/scrim`.

Do not create a large set of extra primitives just to encode every effect opacity. When an effect needs a value the token structure cannot express, keep it in one place, write the dependency down, and include it in the palette-change checks. Full effect construction lives on `1.5 Elevation`.

**Visual: effect color dependency.** One raised card, one focused button and one dialog scrim. Callouts link each effect to its color role. A second row shows the same three after a palette change, with a checklist of what to recheck.

# 2. QA

## Overview

- Base colors, extended palettes and gradients appear in that order.
- Every swatch is a `Doc/Color swatch` bound to its variable, with step, value and contrast annotation.
- Every family has a row note with its purpose; status families carry their status badge.
- No color is shown as text alone, anywhere on the page.

## Tokens geometry

- Each group fills the frame width; its block note stays at `doc/measure/reading`.
- The table fills the frame and is never constrained to the note's width.
- Groups and tables never clip; the frame grows horizontally and vertically.

## Tokens columns

- Name widens for long names.
- Each mode column fits its widest alias chip; extra modes add columns.
- Usage is always visible and fills the remaining width.
- No column is hidden or compressed to keep one canvas size.

## Tokens rows

- Rows use the documentation row height as a minimum and grow when usage wraps.
- Dividers line up across all columns.
- Group separators use documentation spacing.

## Tree

Every role with children shows the parent badge, the vertical connector, an elbow for each child and the indented child badge. At minimum these families show their tree:

```text
color/text/primary         └ on-brand
color/text/secondary       ├ hover  └ on-brand
color/text/tertiary        ├ hover  └ on-brand
color/text/brand           ├ hover  └ pressed
color/border/{tone}        └ subtle
color/surface/base         ├ hover  └ pressed
color/fill/{tone}/{emphasis}  ├ hover ├ pressed ├ selected └ disabled
color/category/{family}    ├ subtle ├ solid ├ text └ border
```

Indentation alone fails QA.

## Contrast pairs

Check every pair in every mode (Light, Dark and any extra mode). Text pairs reach 4.5:1; borders and meaningful icons reach 3:1. A failing pair fails QA until its alias moves.

```text
color/text/{primary, secondary, tertiary, placeholder, brand}   on color/surface/{base, raised, sunken, overlay}
color/text/on-solid, color/icon/on-solid                         on color/fill/{brand, danger}/solid (and any other tone that carries on-solid): rest, hover, pressed, selected
color/text/{danger, warning, success, info, brand}               on color/fill/{tone}/subtle: rest and hover; brand and danger also pressed and selected
color/text/{primary, secondary, tertiary}/on-brand               on color/surface/brand-solid
color/text/inverse, color/icon/inverse                           on color/surface/inverse and color/fill/neutral/solid
color/border/default, color/border/focus                         on color/surface/base and color/surface/raised
```

Also fail QA when an on-solid role sits on `color/fill/neutral/solid`, or when a solid hover, pressed or selected state is lighter than rest under on-solid text without a text role of its own.

The web build runs the same check automatically (`npm run check:contrast`, see `WEB.md`); a failure there is fixed in these variables.

## Copy

Usage copy names a real interface purpose. Filler, or copy that only repeats the token name, fails QA.

## Screenshot check

At normal zoom: Name, every mode and Usage are visible; the table spans the frame; token badges and alias swatches are clearly visible; tree connectors are visible; the Tokens frame does not look like a narrow article column with a cut-off table.

## Guidelines

Fail QA when:
- a topic is text only;
- there is no raw-vs-system example;
- there is no contrast example;
- there is no primitive → semantic → component diagram;
- a palette change is described without before and after components;
- neutral guidance has no same-UI comparison;
- a visual uses names other than this system's token names, or shows another system's names or tools.
